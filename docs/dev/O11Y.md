# Observability of agent runs (O11Y1)

`scripts/o11y/runtrace_bridge.py` turns agent-core run exports into OTLP/HTTP JSON traces: one trace per closed run,
a root `agent.run` span plus one span per audit event (node, agent step, tool call, decision, rule, response,
handoff, interrupt, guard). Python standard library only. Langfuse Cloud is the intended backend (never self-hosted
by us); the default target is a LOCAL receiver, so nothing leaves the machine unless you ask.

## Run it

```
python scripts/o11y/otlp_receiver.py --port 4318 --out spans.jsonl          # local receiver that validates the OTLP shape
python scripts/o11y/runtrace_bridge.py --core-url http://127.0.0.1:8001 \
    --token-file .dev-stack/tokens.json --token-key admin --state o11y-state.json --once
```

Tests: `python -m unittest discover -s scripts/o11y/tests -p "test_*.py"`.

## Targets and configuration (environment only)

| Target | Variables | Rule |
|---|---|---|
| `local` (default) | `PULSO_O11Y_OTLP_ENDPOINT` (default `http://127.0.0.1:4318`) | loopback only |
| `forwarder` | `PULSO_O11Y_FORWARDER_ENDPOINT` (default `http://127.0.0.1:4318`) | loopback only; the local forwarder holds the key (scores go to its `/v1/scores`) |
| `langfuse` | `LANGFUSE_BASE_URL`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` | non-loopback needs https and `--allow-external` or `PULSO_O11Y_ALLOW_EXTERNAL=1`; posts to `<base>/api/public/otel/v1/traces` with Basic `pk:sk` and `x-langfuse-ingestion-version: 4` |

Keys are never printed, logged, put on argv or stored in the state file; error text is redacted. `--env-file F` loads
`KEY=VALUE` lines into the bridge process only (for example the Langfuse env file). The state file holds the runs
cursor, the registry position, exported run keys and a queue of unsent scores. Only closed runs are exported; an open
run holds the cursor back so it is picked up when it closes. `--overlap N` re-reads N positions; duplicates are skipped.

Content: FULL content is ON by default for the `langfuse` target (standing user authorization); `--no-content` or
`PULSO_O11Y_CAPTURE_CONTENT=0` turns it off, `=1` turns it on for other targets. Audit-view events carry no utterances
(only keyed fingerprints), so what is exported is tool args/results, rule inputs, decision values and error text. Bearer
tokens, `sk-`/`pk-lf-` keys, JWTs and `key=value` secrets are always masked (bridge and forwarder). Call, action,
decision, handoff and proposal ids and fingerprints are never exported. No raw bank/E0 rows.

## Forwarder (single egress)

The Rust engine has no TLS or OTel, so `scripts/o11y/otlp_forwarder.py` is the egress: it listens on loopback
(`/v1/traces`, `/v1/scores`), masks secrets, batches, retries with backoff (429/5xx, Retry-After), and spaces requests
under the Hobby limits (ingestion 1000 req/min, public API 30 req/min). Key and URL come from the process environment.

Both OTLP encodings are accepted on `/v1/traces`. Langfuse documents OTLP over HTTP with HTTP/JSON and HTTP/protobuf (no gRPC). `application/x-protobuf` (what the Go OTel exporter in llm-gateway sends) is forwarded byte-exact with the same `Content-Type` and any `Content-Encoding: gzip`, plus the Basic auth and `x-langfuse-ingestion-version: 4` headers. Protobuf is opaque, so it is neither masked nor merged: secret hygiene for those spans is the emitter's job. JSON bodies are masked and batched as before.

```
python scripts/o11y/otlp_forwarder.py --env-file D:\.codexactored\langfuse.env --allow-external
scripts/o11y/run_bridge.ps1 --target forwarder --core-url http://127.0.0.1:8001 --token-file <abs>\.dev-stack	okens.json --state <abs>\o11y-state.json --once
```

`run_bridge.ps1` / `run_bridge.sh` cd to the repo root, so they work from any directory; pass absolute paths for
`--state`, `--token-file` and `--env-file`. Scope: gateway, agent-core and engine only (not the platform). Judges are ours;
Langfuse-managed evaluators are not used, scores stay API scores.

## Story trace id and traceparent

`scripts/o11y/trace_id.py` holds the derivation; `scripts/o11y/fixtures/traceparent_vectors.json` holds test vectors a Rust
implementation must reproduce byte for byte (`pulso.traceparent_vectors/1`; the Python test re-derives them with plain `hashlib`).

```
trace_id        = hex(sha256(utf8("pulso.story.v1" + "
" + finding_key + "
" + run_id)))[0:32]   # finding_key null/absent = ""
span_id(t, *p)  = hex(sha256(utf8("|".join([t] + p))))[0:16]
root span       = span_id(t, "story")
stage span      = span_id(t, "stage", stage, str(attempt))      # attempt = 1 unless the stage is retried
generation span = span_id(t, "gen", role, str(n))               # n = 1-based per role
traceparent     = "00-" + trace_id + "-" + parent_span_id + "-01"   # lowercase hex, no padding
```

Stages: `sensor scout verifier builder recompute compile deliver evaluate dossier`. `finding_key` is the value-loop record
`evidence_ref` (`ev_<16 hex>`, `Finding::evidence_ref`); the run id is the debug-api run id (`value-loop-<job>` for the loop).
REG1's own `finding_key` (metric|dims|counts) is kept as metadata, not as the trace key.

**What the engine sends.** On every llm-gateway and agent-core call made for a finding it adds
`traceparent: traceparent_for(evidence_ref, run_id, <stage of the caller>, attempt)`. The helper
`trace_id.traceparent_for(finding_key, run_id, stage=None, attempt=1)` is the reference (no stage = parent is the root
span). The gateway honours inbound `traceparent`, so its `chat <model>` span becomes a child of the engine's stage span in the
same trace; agent-core needs the same header on its run requests. Caveat: both the engine `generation` span and the gateway span
are generations, so Langfuse can show the cost of one call twice when both are present; the engine generation is the one with
the prompt and response, the gateway one has the provider-side usage (the engine marks its own cost `pulso.cost.source`).

## Engine story spans (`scripts/o11y/engine_trace.py`)

```
python scripts/o11y/engine_trace.py --story-file scripts/o11y/fixtures/engine_story_recorded.json [--finding 0|ev_...]
python scripts/o11y/engine_trace.py --outcome <work>/value-loop/<job>.json --run-id value-loop-<job>     --api http://127.0.0.1:4020 [--token-file f.json --token-key debug]     # events (+ model-calls) from the engine
   [--verdict-file reg1_story.json] [--dossier-file dossier.json] [--model-calls-file calls.json]
   [--target local|forwarder|langfuse] [--allow-external] [--dump otlp.json] [--scores-out scores.jsonl] [--no-send]
```

One trace per finding: root `pulso.story` (session = run id; tags `pulso`, `engine`, `stage:<final stage>`,
`case-type:<kind>`; metadata finding_key, finding_id, metric, outcome_class, reason, data_source), child `stage.<name>` spans
with outcome and error status when blocked or denied, and a `generation <role>` span per model call under its stage (model,
usage, cost from the price table, prompt and response when the engine recorded them). Scores on the trace:
`gate_regression_proven` (BOOLEAN, from `reg1.verdict_story/1`; absent when not evaluated), `rubric_total` (NUMERIC, structural
self-score), `announce` (BOOLEAN; false with comment `not_evaluated` when there is no verdict or dossier), `outcome_class`
(CATEGORICAL: `proposed_delivered`, `proposed_denied`, `blocked_<reason>`, `no_change`, `unlinked`). Local target writes scores
to `--scores-out`; forwarder and langfuse targets send them like the bridge. Content defaults on only for the langfuse target
(same rule and scrub as the bridge, 20000 chars per field).

Timing: stage durations are `recorded` only when model calls carry `duration_ms`; otherwise the finding's window (from the
debug events: previous finding node or `run_started`, to its own node event) is split evenly and spans carry
`pulso.timing=inferred`. No source of time is an error, never an invented clock.

### Data gap and the contract the engine should record

Today the engine persists, per model call, only role, model id, outcome and a short reason (`CallRecord`, via
`Recording` in `engine::models`), and the value-loop record keeps only the model ids ("never model free text"). The debug-api
route `/runs/{id}/model-calls` exists and returns an empty page. So prompts, responses, token usage, per-call timing and per-stage
timing are NOT available; spans for such stories show models and outcomes only, with usage `pulso.usage.recorded=false` and no
cost (no invented numbers). Smallest contract (`pulso.model_call/1`, one record per call, served by `/runs/{id}/model-calls` and/or
appended to `<work>/value-loop/<job>.calls.ndjson`, outside the job store so records stay free of free text):

```
{"schema":"pulso.model_call/1","evidence_ref":"ev_..","role":"scout|verifier|builder","n":1,"model_id":"xiaomi/mimo-v2.6-flash",
 "started_at":"RFC3339 UTC","duration_ms":9200,"tokens_in":812,"tokens_out":215,
 "outcome":"answered|refused|unavailable|invalid","why":"",
 "request":{"messages":[{"role":"system","content":"..."},{"role":"user","content":"..."}],"max_tokens":1024},
 "response":"raw text as returned by the gateway"}
```

Where: `Recording::call` already holds the request and the answer; it needs a clock and the gateway `usage` block. Optional
per-stage timing: `stage_timings[{stage, started_at, ended_at, attempt}]` on the finding record. The fixture
`engine_story_recorded.json` is a RECORDED SHAPE (events and loop outcome follow the engine's code and the b3 live-pass
aggregates; the model calls, verdict and dossier of finding 0 are synthetic illustrations of this contract).

## Mapping

Trace id = `sha256("trace:" + run_id)[:32]`; span id = hash of run and event id (deterministic: re-sends are idempotent).
`langfuse.session.id` = run id. Tags (low cardinality): `agent:<id>`, `release:<id>`, `locale:<xx>`. Metadata
(`langfuse.trace.metadata.*`): agent, release, locale, outcome, closed_by, closed_early, mode, principal_type. Trace
level `langfuse.*` attributes are copied to every span, as the Langfuse docs require for filtering.

| Audit event | Observation type | Reason fields (as `pulso.reason.*`) |
|---|---|---|
| root | agent | outcome, closed_by, closed_early (closed_by is abandonment, escalation, revocation or transfer) |
| node_entered, turn_*, expiry, step_up | span / event | node_type, resume_kind, awaiting, degraded, required_level |
| agent_step, tool_called, action_* | tool | step kind, tool name, status, attempt, gateway error kind |
| decision_made | generation | fallback_depth and fallback flag, provider, model_version, above_threshold, p_cal, tokens, cost |
| command_emitted, rule_evaluated | event | command, flow, interrupt, source, rule result |
| response_emitted / response_failed | generation | validator ok/failures/regenerations, fallback_used, reason_code, tokens in/out, models |
| escalated, handoff_resolved, transfer_* | event | reason_code, queue, priority, resolution, quality |
| injection_flagged, access_denied, knowledge_read | guardrail / retriever | signals, ruleset, scope, reason |

Cost: `gen_ai.usage.cost` is computed from the price table (USD per token, in/out): `xiaomi/mimo-v2.6-flash`
1.4e-7/2.8e-7, `xiaomi/mimo-v2.6-pro` 4.35e-7/8.7e-7, `z-ai/glm-5.3-flash` 1.5e-7/5e-7; an unknown model falls back to
the cost the event reports. Limit: `agent_step` events carry latency but no tokens, so ReAct-node model calls
(for example `pulso-builder`) show cost 0 on the run trace; their real tokens and cost come from the gateway spans
(below). Registry events become one tiny trace each (`registry.<type>`).

Scores (Langfuse target): per trace `run_completed` and `closed_early` (BOOLEAN, deterministic ids, queued and retried,
throttled to stay under the Hobby API limit of 30 requests per minute). `--no-scores` disables them.
`--register-models` creates the three price-table model definitions in Langfuse (idempotent; matchPattern is the exact
name, case-insensitive) so generations are costed from tokens even when no cost is reported.

## Pointing the other emitters at the same backend

- **llm-gateway** (already emits `gen_ai.*`, one `chat <model>` span per call, honours inbound `traceparent`): set in its
  environment `OTEL_EXPORTER_OTLP_ENDPOINT=<receiver base>` (Go appends `/v1/traces`; for Langfuse that is
  `<LANGFUSE_BASE_URL>/api/public/otel`), `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20<b64 pk:sk>,x-langfuse-ingestion-version=4`
  and `OTEL_SERVICE_NAME=llm-gateway`. Prefer a local OTel Collector that holds the key and receives plain OTLP on
  `127.0.0.1:4318`; the gateway then needs no credentials.
- **agent-core** `agent_telemetry`: the explicit form is `setup(endpoint=..., headers=...)`. Note the research report
  `LANGFUSE_INTEGRATION_PLAN_2026-10-05.md` found that `agentcore serve` also reads `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`
  and `..._TRACES_HEADERS` from its injected environment; pass the endpoint and headers explicitly either way. Its
  attribute allowlist drops `langfuse.*`, so its spans reach Langfuse as plain OTel (`gen_ai.*` only). Its own `chat`
  span should stay a plain span to avoid double generations (the gateway span is the generation).
- **Engine linkage**: see "Story trace id and traceparent" above (the engine sends `traceparent` with the story trace id and its stage span id).
- The Rust engine has no TLS client, so external egress is this bridge or a local collector, never the engine directly.
