## Findings

### BLOCKER before deployment to a shared or real-data environment — engine key can mint human approval credentials; all hosts can read the shared secret

**Location:** `docs/adr/0009-shared-core-is-agentcore-serve.md:37-49`; `terraform/modules/hackathon_data/generated.tf:46-50,59-80`.

The PR documents that Agent Core does not impose a per-`kid` role ceiling. It places the engine key in `--staff-keys`, so that key can sign credentials claiming `actor=human`, `role=aprobador`, and step-up, despite the engine code intending never to approve. The same ADR says every workload host can read the whole shared secret and Terraform state contains the private seeds. This is an acknowledged trust-boundary break, not merely an engine coding convention. The ADR says option (a) is the accepted hackathon risk, while the PR body separately says owner sign-off is needed; the connector returned no review/comment establishing who the authorized risk owner is or that this sign-off occurred. The risk is documented, not technically mitigated.

**Failing-test sketch:** use a synthetic key and the pinned Core verifier to sign a credential with the engine `kid`, `actor=human`, `role=aprobador`, `auth.level=step_up`; attempt an approval operation and assert the verifier rejects it. Separately assert the engine/core instance roles cannot retrieve the platform staff seed. The current shared-key arrangement is expected to fail the first negative test and the shared-secret policy fails the second.

**Required disposition:** before a shared or real-data deployment, split per-workload secrets/roles and keep the engine key out of staff authority, or add an upstream per-kid role ceiling. If retaining the hackathon exception, record the authorized owner's explicit acceptance and scope. “The engine never calls approve” is not a security control.

### BLOCKER for end-to-end readiness; not necessarily for merging the Terraform foundation — engine/Core wire contract is explicitly mismatched

**Location:** `docs/adr/0009-shared-core-is-agentcore-serve.md:57-60`; `terraform/modules/hackathon_data/ssm.tf` (`PULSO_CORE_ADDR` / service config additions).

The PR points `PULSO_CORE_ADDR` to Agent Core `serve` on port 8001, but its ADR says the current engine's live client in `real_core.rs` still expects the old core-bridge contract (`PULSO_BRIDGE_ADDR`, human seed/kid and `PULSO_LIVE_*`) and is not provided here. Static tests only check IP-literal wiring; they do not show that the current engine can authenticate or call the new service. The mismatch is honestly disclosed, so this is an integration gate rather than a hidden defect.

**Failing-test sketch:** boot the exact engine revision from `main` against the pinned Agent Core `serve`; execute the configured live Core operation and verify credential issuance, run/registry/export request paths, and response decoding. It should fail on the current mismatched config/client. Add a contract test that would pass only when the engine adapter and Terraform names/ports agree.

### NON-BLOCKER before production use — merge-only secret reseed has a lost-update race

**Location:** `scripts/aws-prod.ps1:700-724` (`Invoke-SeedSecretKeys`).

The command reads and parses the entire current secret once, waits for confirmation, then writes a complete merged JSON version. A parallel rotation/operator update after the initial `get-secret-value` but before `put-secret-value` is overwritten by this stale snapshot, contradicting “every other key is kept.” The interactive confirmation narrows but does not eliminate the race.

**Failing-test sketch:** in the fake AWS handler, mutate an existing out-of-band key after `get-secret-value` and before `put-secret-value`; assert the reseed detects a changed version and aborts/re-reads instead of restoring the stale value. Use a version/serialization guard or re-read-and-compare immediately before writing.

## Disposition

PR #37 has since merged, so these are follow-up gates rather than merge objections. Do not treat its merge as security/deployment approval. The documented key trust issue still needs an authorized owner/scope for any apply/deploy; the Core mismatch blocks an end-to-end claim. No Terraform plan/apply, AWS operation, or branch write was performed.
