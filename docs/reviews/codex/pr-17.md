## Findings

### BLOCKER for upgrading an existing environment — schema change has no migration and documentation instructs DB deletion

**Location:** `backend/src/cc_platform/infrastructure/persistence/sqlalchemy/tables.py:518-570`; `docs/platform/api/improvement-announce.md:50`.

The PR removes a foreign key constraint and adds notification columns (`proposal_id`, `agent_id`, `improvement`), but its changed-file list contains no database migration. The API doc says the fix is to recreate the database by deleting `backend/cc_platform.db`. Fresh-database tests do not demonstrate an upgrade path and deleting an existing DB destroys persisted platform state. That is not safe for any environment with retained records.

**Failing-test sketch:** initialize an old-schema SQLite/Postgres DB with a staff member, notification, and builder proposal; apply the documented migration/upgrade path; assert old rows and constraints remain valid and the new notification fields are readable/writable. The current PR should fail because there is no migration path; deletion is not an acceptable test setup.

**Required disposition:** add an additive, tested migration (including the `registered_by` FK change and notification columns), or explicitly constrain this to a disposable DB-only demo and prevent deployment to any existing stateful environment. Do not merge instructions that make deletion the upgrade procedure.

### BLOCKER for the stated PII-safety contract — detector only rejects two narrow patterns

**Location:** `backend/src/cc_platform/domain/notifications/notification.py:94-105`; `backend/tests/api/test_internal_announce_api.py` PII parameterized cases.

`ImprovementDossier` describes its bounded free text as containing no personal data, but `_bounded` rejects only a regex email and a sequence of nine or more digits with ASCII separators. The API tests cover email/card/phone examples, not names, addresses, dates of birth, account references embedded with letters, or other identifying text. A service token authenticates the caller; it does not make arbitrary free text safe. The current validation must not be described as detecting personal data generally.

**Failing-test sketch:** submit entirely synthetic free text such as `Contactar a Lucia Rojas en Calle 18 #12-34, Bucaramanga` in `problem` and `evidence`; the current regex accepts it. The privacy-safe contract should instead use a typed, allowlisted evidence structure or validated templates that cannot carry customer text/identifiers, with tests proving those rejected/omitted fields never reach a notification or realtime event.

## Positive controls observed

- The internal route requires a service bearer distinct from a staff session and only accepts an existing `auto_detect` proposal.
- It adopts through the registry's read-only `get_proposal`; it does not approve or publish.
- Request text is bounded, evidence links must be case IDs, and the dossier is rendered as text.

## Disposition

Both findings are blocking for stateful rollout/privacy-compliant operation. Local targeted API tests described in the PR do not cover schema upgrade or general PII. No code or database changes were made.
